# 案例回看

用户要求回看或日常发现到期时执行；先读research-controls.md的正式回看、未知分值和样本独立性规则。

1. 读私有analysis/案例日志.md、案例日志维护约定.md、case-reviews.json。显式窗口优先；锚点/来源日期不是到期，观察节点不是正式终评。估计事件日期保留待事件发生状态。
2. 获取原定历史窗的完整日数据，对齐标的/币种/基准/公司行动；当前快照仅补当前跟踪，不能替代历史结果。没有到收盘就不提前给完整日成绩。
3. 方向、路标、机制按原0/1/2表：完整表在日志文末稳定标题`## 打分规则`。机制部分证实或证据不足沿用1；未到/未做为null，不是0。缺原锚或原表没有唯一覆盖时列事实/敏感性/限制，可标“评估完成，有评分限制”，不编新阈值追溯评分。
4. 保留原判断和暂定分，追加有日期的正式回看及错因层；等待需区分解除条件前终值/收盘峰值/盘中峰值，原定义不明并列说明，不能挑有利口径。方向碰巧对但机制错不算方法获证。
5. 每积累4个回看，按下文的口径在私有案例日志追加一轮校准。案例评分与H1账本分开记录，交易记录须经用户确认。
6. 同命题追加、不同命题顺号，旧文不删；整份日志私有。运行npm run build:cases与npm run check:cases，使后台body/html和附件一致。不要仅改Markdown却发布旧导出。

## 跨案例校准

- 先列原判断、回看窗口、实际证据和案例索引。共享同一市场冲击，或在同一窗口重复检验同一命题的案例归为一组。重叠关系有疑问时，保守合并并注明理由、涉及窗口和案例。每组在事实、机制、决策各层最多计一次已确认错误，同层的具体问题仍逐条保留。分层计数与事件组数分别列出。
- 事实层核原数据与口径，机制层核因果解释及其适用范围，决策层核立场、路标和触发条件。按原命题和原窗口判断哪些错误已有证据。证据缺失、回看未到期和评分有歧义的项目单列，分数仍按原规则记录。评分留空时，已经证实的不利结果也要保留。
- 每项注明已验证的改动及其证据，或者列出待验证的问题。流程修订要能对照旧例复核。对阈值、评分分格或触发口径有疑问时，登记现行版本、候选定义和后续检验所需的独立案例。等新案例按事前约定的窗口和基准验证后，再评估是否采用。
